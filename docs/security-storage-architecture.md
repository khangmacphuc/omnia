# Omnia Security and Local Storage Architecture

Status: proposed Phase 1 contract  
Scope: Windows 11 desktop chat application, local-first, multi-provider/BYOK  
Last reviewed: 2026-08-12

This document defines the minimum security and persistence contract for the
first shippable Omnia desktop application. Later IDE, browser, computer-use,
and coding-agent features must extend these boundaries rather than bypass
them.

## 1. Non-negotiable properties

1. Provider API keys, OAuth refresh tokens, proxy credentials, signing keys,
   and database key-encryption keys are never stored in SQLite, settings JSON,
   logs, crash reports, analytics, or renderer/webview storage.
2. Untrusted UI code never receives a stored secret. It may submit a new
   secret once to a narrow native command and subsequently refers to an opaque
   credential ID.
3. All persisted user content is local by default. Cloud sync, telemetry,
   remote backup, and provider-side retention are separate, explicit choices.
4. A workspace folder grant is scoped to its canonical path and permissions.
   Choosing a folder does not grant the application access to arbitrary files.
5. Destructive actions, tool execution, memory promotion, and external network
   access have separate authorization and audit paths.
6. Every schema change is forward-migrated transactionally and verified before
   normal startup. A failed migration leaves the previous database usable.
7. Deleting a conversation/account/provider removes active references and
   queues encrypted blobs and credentials for deletion. UI never promises
   forensic erasure from SSD media or third-party provider systems.

## 2. Trust boundaries

```text
Renderer / webview (untrusted presentation)
        |
        | typed, allowlisted IPC; no arbitrary shell, SQL, file paths, or URLs
        v
Native application core (policy enforcement)
  |         |             |                 |
  |         |             |                 +-- audit / redaction
  |         |             +-- provider gateway (egress allowlist)
  |         +-- storage service (parameterized queries + migrations)
  +-- secret broker (Windows-bound vault / credential handle)
        |
        +-- Windows secret protection

Future agent sandbox (least trusted execution)
        |
        +-- capability broker --> scoped filesystem/network/process operations
```

The renderer is treated as compromised. It can request an operation, but the
native core re-validates identifiers, ownership, path scope, permissions,
state transitions, and size limits. A provider response, imported chat,
attachment, Markdown document, skill, memory, and tool result are all untrusted
data, not instructions to the native core.

## 3. Recommended storage split

### 3.1 Relational metadata: SQLite

Use one SQLite database per OS user/profile. WAL mode gives responsive reads
during streaming writes; enable foreign keys, a busy timeout, and trusted
schema off. All application queries are parameterized and owned by a native
storage module. The UI is not given raw SQL.

Suggested startup pragmas:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
PRAGMA trusted_schema = OFF;
PRAGMA secure_delete = ON;
```

`FULL` is the safe initial durability default. After fault-injection testing,
`NORMAL` may be offered as an explicit performance setting. Checkpoint WAL on
clean shutdown and before a consistent backup. Run `quick_check` periodically
and `integrity_check` after an unclean migration or recovery event.

Do not store large attachment bodies, model files, thumbnails, or full tool
artifacts in SQLite. Keep metadata and content hashes in the database; use the
encrypted blob store for bodies.

### 3.2 Content-addressed encrypted blob store

Blob path:

```text
blobs/v1/<first-two-hex>/<remaining-sha256>
```

The hash is over the plaintext for deduplication inside a profile. Never expose
the hash to remote services as a stable user identifier. Each blob has:

- a random 256-bit data-encryption key (DEK),
- an authenticated cipher (AES-256-GCM or XChaCha20-Poly1305),
- a fresh nonce generated by a CSPRNG,
- associated data containing blob ID, version, media type, and plaintext size,
- an encrypted/wrapped DEK stored in `blob_objects.wrapped_dek`, and
- atomic write semantics: create temporary file in the same volume, flush,
  rename, then commit metadata.

Store only ciphertext in the blob file. A partially written or unauthenticated
blob is never returned. Reference counts are advisory; garbage collection must
recompute reachability inside a transaction before deletion.

### 3.3 Secret vault

The secret broker owns all provider credentials. Preferred implementation on
Windows:

1. Generate a random profile master key.
2. Protect it for the current Windows user with DPAPI (`CryptProtectData`) or a
   carefully reviewed Windows credential-vault integration.
3. Use a derived key-encryption key to wrap per-secret/per-blob DEKs.
4. Store only an opaque `secret_ref` in application tables.

If the selected desktop stack provides an audited encrypted vault (for example,
a native stronghold/credential plugin), it can implement the broker, but it
must preserve the same opaque-handle API. Never fall back to plaintext when
the vault is unavailable. Surface a locked-vault state and require recovery or
re-authentication.

Secret-broker operations:

```text
put_secret(purpose, bytes) -> secret_ref
replace_secret(secret_ref, bytes) -> version
with_secret(secret_ref, operation_descriptor) -> operation result
delete_secret(secret_ref)
probe_secret(secret_ref) -> present | locked | missing
```

There is intentionally no general `get_secret` IPC command. `with_secret`
executes an allowlisted provider authentication operation within the native
process and zeroizes temporary buffers on a best-effort basis. A transient key
entered for a one-off request stays memory-only and is never assigned a
`secret_ref` unless the user explicitly chooses Save.

### 3.4 Search index

SQLite FTS can index message and memory text only when local search is enabled.
An FTS index is another plaintext copy; therefore either:

- encrypt the entire database using a reviewed SQLite encryption distribution,
  or
- exclude sensitive content from FTS and build a keyed/encrypted search index.

Phase 1 should use full database encryption if distribution/licensing permits;
otherwise clearly label the local database as OS-account protected rather than
"end-to-end encrypted." Turning search off deletes and vacuums the FTS index.

Embedding vectors are sensitive derived data. Store locally by default, tie
them to a model/version and source revision, and delete them when the source is
deleted. Remote embedding requires a separate disclosure and permission.

## 4. Data model invariants

The authoritative starter schema is `storage-schema.sql`. Important invariants:

- IDs are application-generated UUIDv7/ULID strings and never provider IDs.
- Provider IDs and remote conversation IDs are optional external references.
- A message is immutable after finalization. Editing creates a new message
  revision/branch, preserving provenance.
- Streaming deltas are batched into a draft; finalize atomically records final
  content, usage, finish reason, and checksum.
- Provider request snapshots include non-secret parameters and model identity,
  but headers, tokens, signed URLs, and raw credentials are redacted before the
  storage boundary.
- Memory is not silently trusted. Candidate extraction and approved memory are
  separate states with source provenance, confidence, scope, expiry, and an
  explicit `user_approved` field.
- Skills are versioned immutable bundles. Local creation/import does not grant
  execution capabilities. Requested and approved capabilities are recorded
  separately and approval is bound to the content hash.
- Workspace grants store a canonical path fingerprint and display path. Before
  every privileged filesystem operation, the live canonical target is checked
  to remain beneath the granted root; junctions and symlinks cannot escape it.
- Soft deletion supports undo and sync reconciliation. A purge queue performs
  hard deletion, blob GC, FTS cleanup, vector cleanup, and vault deletion.

## 5. Database encryption and key hierarchy

```text
Windows user secret protection
    -> profile root key (random; never synced)
        -> database key (HKDF, context = "omnia/db/v1")
        -> wrapping key (HKDF, context = "omnia/blob-wrap/v1")
        -> audit signing key (HKDF, context = "omnia/audit/v1")
```

Prefer a random wrapped database key instead of deriving it directly if the
database engine has key-format constraints. Persist algorithm and key version,
never a raw key. Key rotation is resumable:

1. create a new root/key version,
2. rewrap DEKs in bounded transactions,
3. rekey/replace the database through the engine-supported safe flow,
4. verify every object and a backup restore,
5. retire the old wrapped key only after completion.

Do not invent encryption primitives. Use platform or mature audited libraries,
constant-time verification, authenticated encryption, and CSPRNG nonces.

## 6. Provider/BYOK security

Each provider profile defines:

- type (`openai_compatible`, `anthropic`, `gemini`, `azure_openai`, etc.),
- non-secret base URL and API version,
- opaque credential reference,
- allowed hostname(s),
- optional organization/project IDs,
- TLS and proxy policy,
- model discovery cache and expiry,
- per-provider data-retention disclosure.

Rules:

- Default to HTTPS and reject credentials sent to HTTP endpoints.
- Validate URLs with a real URL parser. Reject embedded credentials, control
  characters, non-HTTP schemes, and ambiguous hostnames.
- For custom providers, resolve and block loopback, link-local, multicast,
  cloud metadata, and private-network targets by default. Offer an explicit
  local-provider grant for `localhost`/LAN runtimes, visibly separate from
  internet BYOK.
- Pin the credential to the normalized scheme/host/port and never forward it
  across redirects to another origin. Prefer redirects disabled.
- Apply connect, header, body-idle, and total timeouts; response byte limits;
  decompression limits; cancellation; and bounded retry with jitter.
- Redact `Authorization`, API keys, cookies, signed query strings, request
  bodies marked sensitive, and model output from diagnostics by default.
- Model discovery data is untrusted. Enforce length/count limits and render it
  as text, never HTML.

## 7. IPC and renderer policy

Expose small typed commands such as:

```text
conversation.create(input)
conversation.list(cursor, filters)
message.append_draft(conversation_id, generation_id, chunk)
provider_profile.save(metadata, secret_input?)
provider_profile.test(profile_id)
workspace_grant.add(folder_picker_token, permissions)
blob.open(blob_id) -> one-use stream handle
memory.approve(candidate_id, edits)
```

Every command has:

- strict schema validation and unknown-field rejection,
- maximum sizes/counts and pagination,
- an authenticated local window/session identity,
- object ownership checks,
- cancellation and bounded execution,
- structured error codes with no stack traces or secrets,
- an audit category where appropriate.

Never expose generic `read_file`, `write_file`, `fetch`, `spawn`, `sql`, or
`invoke(method, args)` commands. Disable webview developer tooling in release,
remote navigation, arbitrary new windows, insecure mixed content, and drag/drop
navigation. Use a restrictive Content Security Policy with no remote scripts,
no `eval`, and packaged immutable frontend assets. Sanitize Markdown/HTML and
open external links through an origin-checked native confirmation flow.

## 8. Memory and skill safety

Automatic memory must be useful without becoming prompt-injection persistence.

Memory pipeline:

```text
source message/tool result
  -> candidate extraction (untrusted)
  -> secret/PII scan + policy classification
  -> deduplicate/conflict detection
  -> user rule or explicit approval
  -> scoped memory record
  -> retrieval with provenance labels
  -> prompt assembly in a distinct data section
```

Never store API keys, authentication codes, recovery phrases, private keys, or
passwords as memory. Default candidate retention should be short (for example,
seven days); approved memory can have explicit expiry. Users can inspect why a
memory was recalled, edit it, disable it, or delete it with derived embeddings.

Skill packages need a manifest, immutable version, content hash, author/source,
requested capabilities, and optional signature. Treat skill instructions as
untrusted content. Installing, enabling, granting capabilities, and executing
are separate actions. Any edit or upgrade invalidates prior capability approval
unless its approved content hash remains identical.

## 9. Audit, privacy, and diagnostics

The audit log records security-relevant metadata, not chat content or secrets:

- provider credential created/replaced/deleted,
- workspace grant created/changed/revoked,
- export/import/backup/restore,
- memory approval and skill capability approval,
- policy denial and tool confirmation,
- database recovery/key rotation.

Use an append-only hash chain or keyed MAC chain to make accidental tampering
evident. Rotate locally, cap storage, and allow export. It is not an enterprise
non-repudiation system.

Diagnostics are opt-in and previewed before export. Produce a structured bundle
with a redaction pass and a second validation pass. Use allowlisted fields
instead of trying to redact arbitrary logs after the fact. Crash handling must
avoid process dumps containing model prompts or provider credentials unless the
user explicitly enables a developer diagnostic mode.

## 10. Backup, export, import, and deletion

### Backup

Create a consistent snapshot through the SQLite backup API or a coordinated
checkpoint, include encrypted blobs, and write a signed manifest of hashes and
versions. The default backup remains encrypted with a user-chosen recovery key;
the Windows-bound profile key alone is not portable. Test restore into a new
temporary profile before reporting a backup as verified.

### Export

Export is plaintext only after a prominent confirmation. Default exports omit
credentials, hidden system prompts, raw provider headers, audit details,
workspace paths, memory, and skills unless selected. Sanitize filenames and
prevent archive path traversal.

### Import

Treat imported databases/archives as hostile. Parse in an isolated temporary
area with byte/count/depth limits, verify manifest/hash/version, reject absolute
and parent-relative paths, scan skill manifests, and commit only after full
validation. Never open an imported database directly as the live database.

### Deletion

Deletion flow:

1. tombstone the entity and hide it from active queries,
2. remove search/vector derivatives,
3. decrement or recompute blob reachability,
4. purge unreachable encrypted blobs,
5. delete associated secret-vault entries,
6. checkpoint and optionally vacuum on a maintenance schedule,
7. disclose provider-side retention and backup limitations.

## 11. Migration and recovery contract

Database header table stores schema version, minimum compatible app version,
migration state, and creation time. Each migration has a stable ID and checksum.

On startup:

1. acquire a single-writer profile lock,
2. verify available disk space and database integrity,
3. create a verified pre-migration backup,
4. run one migration transaction at a time,
5. validate foreign keys and invariants,
6. record migration ID/checksum/timing,
7. only then allow UI writes.

For transformations too large for one transaction, use an explicit resumable
state machine with old and new representations readable until cutover. Never
silently downgrade. A newer incompatible database opens read-only with a clear
message and export option.

Recovery order:

1. retry read-only and inspect integrity,
2. restore the latest verified local snapshot,
3. salvage to a new database while preserving the corrupt original,
4. never delete the original without explicit confirmation.

## 12. Security gates before Phase 1 release

- Threat model reviewed for renderer compromise, malicious model output,
  malicious provider endpoint, imported archive, and local malware limitations.
- IPC allowlist and permission tests prove the renderer cannot access secrets,
  arbitrary filesystem paths, raw network calls, SQL, or process execution.
- Secret scanner confirms no credentials in database, logs, diagnostics,
  exports, crash events, clipboard history created by Omnia, or source control.
- Migration tests cover every supported version, interrupted migration, disk
  full, corrupt WAL, locked file, and downgrade.
- Storage tests cover power loss at each blob write step, concurrent streams,
  cancellation, duplicate content, GC, restore, and key rotation.
- Provider gateway tests cover redirect credential leakage, DNS rebinding,
  private/metadata addresses, oversized/decompression-bomb response, malformed
  SSE, stalled streams, TLS failure, proxy failure, and log redaction.
- Markdown and artifact renderers pass an XSS suite; external navigation and
  custom protocols require policy approval.
- Import tests include archive traversal, symlink/junction escape, nested
  archives, malformed databases, billion-laughs-style inputs, and huge counts.
- A clean Windows VM uninstall/reinstall test confirms whether local data and
  credentials are retained or removed exactly as the UI promises.

## 13. Delivery phases

### Phase 1A: foundations

- SQLite schema/migration runner and repositories
- profile lock, integrity check, safe backup/restore
- Windows secret broker with opaque handles
- provider egress gateway and redacted structured logging
- encrypted content-addressed blob store
- conversation/message streaming transaction model

### Phase 1B: complete chat storage

- branches, revisions, attachments, artifacts, usage/cost records
- local search and optional embeddings
- provider profiles/model caches/presets
- import/export, retention settings, purge/GC
- memory candidate/approval/provenance lifecycle
- versioned skill registry without execution

### Phase 2+: privileged tools

- capability broker and approval receipts
- agent execution sandbox
- scoped workspace file index
- browser/network policy and computer-use isolation
- signed skill packages and granular runtime grants

No Phase 2 tool receives direct database keys, provider credentials, or an
unrestricted native-core handle.
